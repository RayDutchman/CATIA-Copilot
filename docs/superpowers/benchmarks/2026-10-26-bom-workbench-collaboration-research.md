# BOM 工作台与 CLI/Skill 协同调研

## 1. 目标与结论

目标是让用户及时看见并掌控 agent 对 BOM 的修改，同时保留 CLI 独立运行能力。本文是静态源码调研与方案比较，不代表新接口已经实现；未修改业务代码、未操作 CATIA。

核心结论：问题不是简单增加几个 BOM 命令，而是决定**谁拥有写入、显示和撤销的上下文**。现有工作台并非离线编辑器，CLI 也没有可直接调用的工作台远程接口。

## 2. 已核实的现有行为

| 事项 | 代码证据 | 实际行为 |
|---|---|---|
| 工作台入口 | `catia_copilot/ui/catia_embed.py`：MENU_BOM_EDIT | 打开 V3 BomEditDialog，不同于独立 BOM 导出窗口 |
| V3 数据模型 | `catia_copilot/catia/bom_collect_v3.py`：collect_bom_part_masters | 主数据与实例分离；含 COM 引用，不是可持久化协议 |
| 三种视图 | iter_full_rows、iter_hierarchical_rows、flatten_bom_to_summary | 完整实例、同父层级合并、汇总；不是三份独立可编辑数据 |
| 普通字段 | `bom_edit_dialog_v3.py:1433`：_on_item_changed | 通常先改缓存、立即写 CATIA，失败回滚本次缓存/显示 |
| PN 改名 | rename_part_master、_is_pn_conflicting | 保留窗口内 pm_key，更新 PN 及关联显示；已有业务约束应复用 |

| 批量编辑 | `:1773`：_apply_cell_values | `(row_idx, col, new)` 逐项写回，成功项合成一步历史；不支持把实例名/实例描述当主数据批填 |
| 历史 | `:1906–1937`：_push_undo、_undo、_redo | 内存列表，动作 `(key, col, old, new)`；字符串key代表主数据，整数key代表实例 |
| 撤销执行 | `:1939–2024`：_apply_field_changes | 尝试写 COM，但部分分支忽略失败，仍移动历史并更新显示 |
| 局部刷新 | `:3343`：_refresh_rows_from_catia；refresh_row_from_com | 可按相关子树增量更新属性，不重建整树；没有同步 undo/redo，也不处理实例名 |

| 关闭 | _on_cancel、done、closeEvent | 修改已经即时写回；没有统一“提交全部暂存编辑”的阶段 |

上述 UI 方法均在 `catia_copilot/ui/bom_edit_dialog_v3.py`，除表格另注明外。

### 必须修正的理解

- “整批作为一个原子步骤推入历史”只是一次撤销的分组，**不是 CATIA 事务**；中途失败不保证全批回滚。
- 没有证据支持一份独立的待提交脏字段库；用户当前打开的单元格编辑器，与已写回缓存是不同状态。
- 局部刷新不等于历史同步。刷新后旧撤销动作仍可能覆盖外部刚写入的值。
- QSettings 保存模式、列及交互偏好，不保存完整 BOM 工作对象。
- `inst_key=id(product)` 仅在当前进程有效；窗口内 pm_key 也不能直接承诺跨重载永久稳定。

## 3. 与当前 CLI 的差距

现有 `bom collect/export/write` 对应旧采集、独立导出与按 PN 批量写入，并不覆盖 V3 工作台编辑语义。

- 可复用：V3 采集/三视图、主数据访问与改名、`bom_write.write_cell` 的字段写入规则、受影响行刷新。
- 需最小提取：字段变更执行结果、批次历史与失败处理。目前这些分散在 Qt 控件回调里，不能直接把 `_on_item_changed` 当远程 API。
- 需新建：跨进程请求或通知通道、可序列化目标引用及请求状态。进程内 Qt signals 和现有 task JSON 均不是现成的 GUI IPC。
- 不应搬迁：树控件、选区、列宽、快捷键等纯 GUI 交互。
- 旧按 PN 批量写回接口缺少可靠逐项结果，不能凭任务结束就推断所有单元格写入成功。

## 4. 三种方案

### A：CLI 写入，GUI 观察并增量同步

`CLI worker → CATIA → 写入结果/变更通知 → GUI 更新受影响数据与显示`

- 保持 CLI 独立执行，GUI 不在线也能完成；复用现有增量刷新。
- GUI 可显示开始、进度、已写回和同步失败，失败通知不应触发重复写入。
- 需要新通知通道；可评估复用任务记录作为结果来源，而非直接新增 HTTP 服务。
- 最大难点是历史：GUI 不能继续把旧 undo/redo 当作当前正确基线。需失效相关历史或明确协调，不能只刷新文本。
- 更适合“GUI 用于实时观察；agent 改动不要求进入同一撤销历史”的需求。

### B：工作台在线时，由工作台统一执行编辑

`CLI 请求 → 工作台认领 → 共用字段执行器 → CATIA + 缓存 + UI + 批次历史 → 回执`

- 人工与 agent 的编辑可按同一顺序执行，能把一批 agent 修改纳入工作台撤销历史。
- CLI 仍保留不依赖 GUI 的执行路径，但必须在请求被认领前确定执行端；GUI 已接单后的超时不能自动改走 CLI 再写一遍。
- 新增通道、窗口会话定位、请求认领与回执；并非把现有 GUI 函数暴露出来就完成。
- 现有 GUI 多处在主线程调用 COM，直接执行大批量循环可能使界面不刷新。需分步调度，或另行设计合法 STA 执行边界，不能跨线程传递现有 COM proxy。
- 更适合“工作台是人和 agent 共同编辑的界面，要求统一撤销”的需求。

### C：共享离线 BOM 快照

可支持离线分析、审阅和事后对账，但不能替代 A/B 的执行所有权、实时通知和并发协调。当前没有现成的无损快照格式，第一阶段不建议作为前置工程。

## 5. 两个具体冲突

**刷新与撤销冲突**：用户将 Revision 从 A 改成 B；CLI 改成 C；GUI 刷新显示 C。原 undo 仍可能直接写回 A，覆盖 C。仅自动刷新不解决这个问题。

**编辑器与 agent 冲突**：用户正在输入某字段，agent 同时完成该字段写入。随后用户提交编辑器里的值，会覆盖 agent 结果。这里需要处理的是正在编辑的字段和执行顺序，不是假设已有离线草稿库。

多工作台同时编辑同一文档也有同类问题。任何方案都应明确同字段冲突；不需要因此给每个单元格加审批步骤。

## 6. 最小共同基础

1. 复用现有字段规则，提取 Qt-free 的变更描述与逐项结果；主数据与实例字段明确分开。
2. 保存每项 old/new、是否已写回、错误和来源；仅成功项进入可撤销集合，未知结果不能算成功或自动重试。
3. 修正 GUI undo/redo 的失败处理；刷新影响历史时给出明确语义，不让显示与 CATIA 静默分离。
4. 目标引用不传 COM 对象、裸 `id(product)` 或视图行号。在线工作台可采用窗口会话/加载代次内有效的引用，重载后失效；无需一开始承诺永久跨会话身份。
5. 同一个请求 ID 在执行端只认领一次；CLI 超时继续查询原请求。不把“参数恰好相同”永久判作重复，以免阻止合法的新操作。

这些是协同正确性的基础，不是另建通用框架或统一审批/verification 门禁。

## 7. 用户应能看到什么

- 当前操作来源（人工/agent）、目标文档、影响的行/字段及批次进度。
- 区分“请求已接收”“已写回 CATIA”“GUI 已同步”“文件已保存”，不能合并成一个成功灯。
- 部分成功时看得到成功、失败和结果未知的条目；重复引用的共享属性同步展示。
- 停止批次只停止后续尚未执行的项，不伪称中断当前 COM 调用或撤销已经写入的数据。
- 如需撤销 agent 整批改动，必须基于成功项及当前数据状态处理，不能盲目套用旧值覆盖后来的人工作业。

## 8. Skill 的集成方向

保留短入口索引，新增 BOM 专用参考：三种视图的选择、共享属性/实例属性区别、工作台会话目标、批次结果判读、查询原任务、保存与导出范围。

Skill 不操纵 GUI 坐标，也不要求所有工作都启动 GUI；命令与返回字段应在方案定案后来自真实 schema。现有建模继续 `run --file`，与 BOM 协同分开。

## 9. 建议与待决问题

先确认一个产品要求：**agent 的修改是否必须能在 GUI 工作台中，作为一批直接撤销？**

- 如果只要求实时看见结果，优先评估 A，改动较小；同时明确外部变化影响的历史如何失效。
- 如果要求人工/agent 共用撤销和编辑顺序，倾向 B，并保留独立 CLI 路径；先修共同执行/历史基础，不直接包装现有 UI 回调。
- C 暂不作为前提。文件移动/改名等外围能力、自动打开工作台和预览审批均未纳入本轮决定。

当前只完成调研；没有选择或实现新的协同模式，也没有改动主目标规格。
